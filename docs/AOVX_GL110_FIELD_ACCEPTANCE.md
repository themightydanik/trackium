# GL110-GL read-only diagnostics and field acceptance

## Existing observability

- TCP framing and the raw PostgreSQL journal already record receive time, parser/checksum outcomes and the original packet. A per-BCD observation row records the last packet seen; the global observation CLI is operator-only.
- Tenant enrollment explicitly binds a physical registry record to an active BCD identifier. The bounded worker normalizes eligible 0x0200 packets, records pending/terminal state and links each processed packet to an immutable tenant observation. An exact replay can link a new packet to an existing observation.
- Parser `aovx-gal-v2` preserves BCD and reports UTC separately from Gateway receipt. Lite already displays history and a last-known unverified real-time position. The AL300-LA golden frame verifies protocol decoding; GL110-GL hardware behavior remains to be measured.

## Diagnostic contract

Open the physical device in Lite and select **Load diagnostics**, or send an authenticated `GET /v1/devices/{device_id}/diagnostics` with the existing `read` scope. Results are snapshots. Select the button again for an updated snapshot. The endpoint returns 401 for unauthenticated requests, 403 for missing read scope and 404 for an out-of-tenant or nonphysical device. It requires an active binding to show packet and decoded observation metadata. Pre-binding packets and observations, including those from a previous binding of the same record, are excluded. Disabling or revoking the binding hides the last-known position. The underlying observation history is retained.

| Field | Meaning |
| --- | --- |
| `binding`, `enabled`, `trust` | Current registry/enrollment state. AOVX trust is always `unverified`. |
| `packet`, `packet_recency` | Last identified packet for the active binding, including non-telemetry frames. Receive time is UTC. `no_recent_data` means none seen or the last was more than 15 minutes ago. This threshold is independent of GNSS eligibility. |
| `packet.decoding`, `packet.ingestion` | Redacted packet classification and latest journal state. Rejected packets or failed parsing/checksum show a processing failure. Pending means queued or retryable; the journal provides no durable attempt/error classification for a worker transaction that rolled back. |
| `observation` | Latest successfully normalized logical observation in receipt order, parser version, Fix/Unfix, Real-time/Buffered, receipt and device UTC. Payload flags can be unknown on older observations. A duplicate can advance packet receipt without changing this observation. |
| `observation.packet_ref` | Reference to one raw journal packet already linked to the tenant observation. Resolving it requires separate authorized operator access. The endpoint returns no raw bytes, BCD identifier, IP address, sequence, or underlying exception. |
| `observation.receive_lag_ms`, `observation.clock` | Receipt minus measurement. A negative value identifies a future reported time. Malformed UTC is reported separately. A positive value includes device clock offset and transport delay; it cannot attribute either cause. |
| `last_valid_gnss_at` | Greatest normalized GNSS measurement time under the active binding, including buffered history. |
| `position` | Whether the latest decoded observation qualifies and why, latest selected measurement time, and whether the newest eligible UTC second contains conflicting coordinates. The latest observation and last-known position can differ. |

A real-time position needs a v2 valid fix and a Gateway receipt between zero and five minutes after measurement. Buffered reports, invalid fixes or timestamps, and backward jumps outside the lag window cannot become last known. A timely but earlier fix cannot override a newer measurement. If eligible fixes at the newest second disagree, the last-known result is unavailable until newer eligible data arrives. A retained last-known fix can be old, even when no data is recent. Route, checkpoint, geofence and proof decisions remain gated against unverified physical observations.

## Physical field procedure

Use an approved test tenant, an already configured GL110-GL and its normal reporting cadence. Agree the observation window and independent coordinate accuracy tolerance before starting. Record tracker model and firmware, UTC reference and its uncertainty, Gateway revision, test record IDs, expected report cadence and relevant site/network conditions. Keep a redacted UTC timeline with the diagnostic snapshot and last-known result before and after each step. Use packet references for operator correlation. Keep raw exports, identifiers, and precise routes in approved private evidence storage.

| Step and action | Expected and pass/fail criterion | Evidence to collect |
| --- | --- | --- |
| 1. Observe the first report on the existing connection. | With enrollment active, the last packet advances within the agreed cadence. A valid 0x0200 reaches processed and has a linked observation. A registration or other frame can arrive first. Fail if a matching report is visible to another tenant or an accepted telemetry report never becomes processed. | Initial/after snapshots, timestamps, packet ref, parser version. |
| 2. Stay stationary outdoors with open sky until Fix. | Fix and Real-time are reported. Eligible measurements agree with the independently measured location within the agreed tolerance; receive and measurement times are distinct. If Unfix is observed initially, it supplies no last-known fix. Fail on out-of-bounds coordinates or an Unfix promoted to position. | Reference coordinates/time and uncertainty, history point and snapshot. |
| 3. Walk or drive an approved short route. | History shows discrete valid fixes near known markers in their reference time windows. Last-known time advances only with newer eligible fixes. Fail on a reversed hemisphere, unexplained position regression, or physical data triggering shipment transitions. | Timed waypoint notes, history view, shipment state and ledger before/after. |
| 4. Allow a temporary approved network outage or visit a planned coverage gap. | No packet time advances during the gap. After 15 minutes the snapshot says no recent data. The old last-known fix remains explicitly last known. Fail if the interface claims a new fix during loss. | Start/end UTC, packet recency and map before/during. |
| 5. Restore normal connectivity and observe backlog. | Buffered reports can enter history, but never replace the last-known fix. A delayed real-time report outside the lag window cannot replace it either. Pass buffered delivery only if buffered samples are actually observed. | Reports sorted independently by receipt and measurement, buffered flags and last-known snapshots. |
| 6. Observe an authorized local hardware restart. | Post-restart packets resume within the agreed window. Any backward, invalid or future timestamps are diagnosed without regressing the prior position. If the clock never resets, record the reset branch as NOT OBSERVED. The procedure sends no restart command to the tracker. | Power-cycle timeline, first post-restart packet, clock and position snapshots. |
| 7. Compare clock and lag at multiple points. | Compare fresh measurements with a synchronized independent UTC reference when network conditions are stable. Document drift/uncertainty against the agreed tolerance; a large lag during network loss alone is inconclusive. Fail on repeatable timezone offset or unstable time outside tolerance. | Reference clock source, paired receive/measurement times and lag trend. |
| 8. Observe a naturally repeated frame, if one occurs. | Same frame advances packet receipt and adds lineage without another logical observation, cargo event or proof. Same-second conflicting eligible coordinates suppress the position. If repeat/conflict does not occur, record that hardware branch as NOT OBSERVED. Never inject an artificial report into the real tracker connection. | Two transport appearances, one event ID, ledger count and separate local regression result. |

All eight device scenarios require physical acceptance. Automated PostgreSQL and Chromium use controlled reports and cover receipt/UTC separation, older and delayed time (including a modeled reset), future and malformed time, Unfix and invalid positions, buffering, conflict, replay, and scope. They cannot demonstrate this unit's clock drift, GNSS accuracy, network behavior or restart behavior.

## Performance, rollout and rollback

There are no migrations, new write-path queries, changes to logging, or polling calls for diagnostics. Each button press makes two reads (tenant registry lookup and one snapshot statement). Packet lookup uses the BCD observation primary key and existing journal receive-time index; lineage uses the existing tenant/device/event index. Eligible and historical measurements can scan or sort the active binding's per-device telemetry history. The existing location projection also checks the indexed active binding. Production-scale read latency has not been measured.

Before authorized rollout, run the local tests and check the on-demand read on a representative nonproduction tenant. Confirm rebinding or revocation clears the last-known projection and that historical rows remain available to their authorized tenant. Reverting the application revision removes the endpoint and UI and restores the previous location projection; it requires no DB restore. Historical evidence, parser versions, packet links and proofs are preserved.
