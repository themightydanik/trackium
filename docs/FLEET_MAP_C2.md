# Fleet Map · C2 road route planner

The planner lives in the existing authenticated Fleet Map. Select a shipment, then choose **Plan from checkpoints** or **Start blank route**. Enter latitude and longitude, or choose **Pick on map** and tap the canvas. With keyboard focus on the map, Enter uses its center. Add up to eight intermediate stops and use the waypoint controls to reorder or remove them. Passenger car uses no truck parameters. A truck calculation requires height, width and length in metres, plus gross and axle weights in metric tonnes.

**Calculate route** sends the [B2 request](GATEWAY_ROUTING_API.md) through the existing same-origin session and CSRF client. Dispatcher, Admin and Owner need the `shipments` scope. Viewers retain their B3 inspection access. Gateway remains responsible for authorization, input validation and limits. No client-side routing is used. The draft uses editable dotted points, the preview uses a violet dashed line, the shipment plan stays gold, and the active B3 route stays mint. GPS remains independently sourced from eligible telemetry.

A single in-memory draft belongs to the selected shipment in the current authenticated session. Editing clears the preview and aborts the request. Only the current draft and its matching controller can apply a response. Duplicate submission while a request is pending is ignored. Network, HTTP and validation errors provide a recovery action or the relevant field guidance. The original request is never automatically retried. Switching shipments or leaving prompts before discarding edits. Logout, role loss, company changes and session expiration clear protected state. The planner uses the existing Leaflet canvas, polling and bounded polyline6 decoder. A calculation neither starts another polling timer nor moves the camera. **Fit preview** explicitly changes the camera, and **Return to fleet view** discards the draft.

The preview gives the road estimate, ordered stops, graph metadata and optional maneuver instructions as plain text. It excludes traffic, border queues and mandatory rests. HGV results are planning estimates and restrictions may be incomplete. There are no B3 writes, proposal management or changes to Cargo, GPS or proof records.

## Validation and captures

The browser fixture checks 1440, 768, 390 and 320 px, keyboard and touch input, delayed and concurrent responses, edited stops, road/GPS layers, Viewer access and session changes. The single local instrumented Chromium run measured 315 ms at 1440 px and 269 ms at 390 px from requesting a calculation to seeing the preview, including test browser interaction and intercepted API time. These measurements are not production route latency.

The private routing workflow runs an additional Chromium acceptance test against Gateway, disposable PostgreSQL and Valhalla 3.6.3. It creates real customer sessions, accepts a Dispatcher invitation, calculates and fits the fixture route, and compares the persisted shipment and revision list before and after. The only write during planning is the standalone non-persisting calculation request. The pinned synthetic graph tests the deployed network and API wiring. Regional routing coverage and physical Android WebView acceptance remain separate gates.

Reproduce the synthetic-browser screenshots with `TRACKIUM_PLANNER_SCREENSHOTS=/path/to/output node --test tests/minidapp/route-planner.test.cjs`. Use the existing UI toolchain setup. For the real browser route test, start the disposable private routing Compose fixture using the [B2 operating instructions](GATEWAY_ROUTING_API.md), then run `node --test tests/minidapp/route-planner.private.cjs` with Playwright available and the same Compose environment. C3 can connect the draft to explicit proposal persistence and lifecycle controls.
