# Minima Proof Engine v1

This extends the existing Free/Managed Gateway, cargo event journal and transactional outbox. It does not add Integritas or change the GL110-GL/legacy MiniDapp. Publication defaults to **disabled**. There has been **no real Core/network transaction validation in this development environment**. The automated integration tests use real PostgreSQL and a clearly mocked Minima RPC. Live operation requires the operator checks below; this is not a production-readiness claim.

## Protocol and researched Core interface

The server signs a small, self-transfer Minima transaction using a dedicated address in a private Core wallet. Its transaction STATE port **250** holds 38 bytes:

```
TRKP (4 bytes) | version 01 | flags (1 byte) | SHA-256(public commitment JSON) (32 bytes)
```

Flags: bit 0 = synthetic, bit 1 = test; remaining bits zero. Example prefix for synthetic live data: `0x54524b500101…`. Test commitments have a different domain input (`publish_mode`) and flag, never a real TXID. There is no GPS, temperature, customer name, tenant identifier or key in the STATE bytes. Hash commitments can still reveal correlations; exported bundles contain sensitive cargo data and must be shared deliberately.

The public commitment JSON is serialized with the existing recursively key-sorted JSON canonicalizer (UTF-8, schema v1). Fields are:

```
domain = "trackium:cargo:minima-proof:v1"
schema_version = 1
publish_mode = "live" | "test"
chain_id, publisher_address
event_id, shipment_id, event_type, sequence
canonical_sha256, previous_hash, source_trust
```

`canonical_sha256` hashes the exact immutable `cargo_events.canonical_payload` UTF-8 bytes. That payload includes tenant, device, event time and data. `previous_hash` links every cargo event, including events not selected for publication. The bundle contains the complete prefix from sequence 1 through the anchored event. A prefix proof does not claim that no subsequent records exist. Source trust is immutable: anchoring synthetic/unverified input never makes it a physical truth or a verified tracker reading.

Both local cargo hashing and commitment hashing are **SHA-256**. Minima's default object hashing is **SHA3-256**, used by Core for its transaction/TxPoW identifiers. The engine does not relabel a local SHA-256 as a Minima hash or attempt to implement Minima's binary serialization/consensus in JavaScript.

Sources inspected: official [minima-global/Minima commit 52542f2](https://github.com/minima-global/Minima/tree/52542f25605a28a776e9b3b43b0808a05dceab01), reporting Core **1.0.49.4**. The live writer rejects another version until its command contract is reviewed. Relevant source files:

- [txnaddamount](https://github.com/minima-global/Minima/blob/52542f25605a28a776e9b3b43b0808a05dceab01/src/org/minima/system/commands/txn/txnaddamount.java): explicitly restrict inputs/change to `fromaddress`.
- [txnmine](https://github.com/minima-global/Minima/blob/52542f25605a28a776e9b3b43b0808a05dceab01/src/org/minima/system/commands/txn/txnmine.java): mines without posting, returns the final TxPoW ID and serialized TxPoW, with a 120-second mining limit.
- [txnminepost](https://github.com/minima-global/Minima/blob/52542f25605a28a776e9b3b43b0808a05dceab01/src/org/minima/system/commands/txn/txnminepost.java): posts that already mined artifact.
- [txpow](https://github.com/minima-global/Minima/blob/52542f25605a28a776e9b3b43b0808a05dceab01/src/org/minima/system/commands/search/txpow.java): transaction lookup, onchain and block queries.
- [Crypto](https://github.com/minima-global/Minima/blob/52542f25605a28a776e9b3b43b0808a05dceab01/src/org/minima/utils/Crypto.java) and [RPC handler](https://github.com/minima-global/Minima/blob/52542f25605a28a776e9b3b43b0808a05dceab01/src/org/minima/system/network/rpc/CMDHandler.java).

The engine uses these actual commands (values validated/generated by the server):

```
status
txnlist id:trk_<commitment_sha256>
txncreate id:trk_<commitment_sha256>
txnaddamount id:... amount:0.001 address:<publisher> fromaddress:<publisher> tokenid:0x00 burn:0 storestate:true
txnstate id:... port:250 value:<wire_commitment>
txnbasics id:...
txnsign id:... publickey:auto
txncheck id:...
txnexport id:... showtxn:true
txnimport id:... data:<saved_signed_row>  # recovery only, if custom row disappeared
txnmine id:...
txnminepost data:<saved_mined_artifact>
txpow txpowid:<final_txpow_id>
txpow onchain:<final_txpow_id>
txpow block:<inclusion_height>
```

`txnpost`/automatic-post signing are deliberately not used: an ID reported before asynchronous mining is not the final mined TxPoW ID. The publisher never supplies a seed/private key to an RPC command. It asks the node's own wallet to sign. The 0.001 self-transfer requires spendable funds at the configured address; burn is zero. Only standard `RETURN SIGNEDBY(0x...)` wallet scripts are supported; anyone-can-spend/custom-contract publisher addresses are rejected. Use a dedicated wallet/address and no concurrent external spending, and monitor wallet signing-key use limits.

## Migration, durable publication and states

Migration `003_proofs.sql` is additive and checksum tracked. Existing raw packets, telemetry, cargo events and outbox delivery state remain intact. It adds `proof_enqueued_at`, proof records, RPC attempt records and state history. Commitment identity, policy, signed artifact and final mined artifact become immutable. Proof uniqueness is `(event_id, mode)`, so a local test receipt never suppresses a later live proof.

Selected types: `shipment_created`, `status_changed`, `checkpoint_reached`, `temperature_violation`, `temperature_recovered`, `route_deviation`, `route_recovered`. Routine telemetry, edits and simulator controls remain in the hash chain without a transaction per sample. Test mode leaves the existing outbox state and live enqueue marker untouched. Live enqueue records a durable proof row before setting the marker. Generic outbox `processed` is never interpreted as chain confirmation; the proof consumer is independent of another consumer's lease/state.

A PostgreSQL session advisory lock serializes publisher ticks across Gateway processes sharing this database. Enqueue batches are at most 100. Publication is globally serial for this wallet, and selected predecessors in a shipment must be confirmed first. A blocked or ambiguous spend blocks new spends, favoring safety over throughput. Do not share the publisher wallet across separate databases/Gateways.

The signed row and transaction ID are checkpointed **before mining**. The mined blob, SHA-256 of that blob's stored hexadecimal text, and final TxPoW ID are checkpointed **before broadcasting**. After a crash/timeout the worker queries the known ID first, then may rebroadcast only that identical saved blob. It never automatically constructs another transaction once the mined artifact exists. A mining response lost before checkpoint is safe to re-mine because mining did not post. RPC attempts record start, sanitized response/hash, outcome and error code. A process crash can leave an attempt `started`; recovery uses persisted artifacts, not the attempt's outcome.

| State | Meaning |
| --- | --- |
| pending | durable work; no broadcast |
| submitting | broadcast about to occur or its result ambiguous |
| submitted | post accepted or TxPoW known; not proof of inclusion (test mode: local receipt only) |
| included | observed on the current chain, below configured depth |
| confirmed | observed current-chain depth reached; subject to reorg and freshness |
| retryable_error | node unavailable, pruning/lookup unavailable, or bounded transient publication error |
| failed | permanent validation error or exhausted publication budget; requires operator investigation |
| reorged | previously recorded inclusion block replaced on the observed chain |

Publish retries use exponential backoff (up to five minutes) and at most `PROOF_MAX_ATTEMPTS` (default 5, max 10). The same limit bounds broadcast attempts. No automatic rebuild/reset of exhausted artifacts is exposed. A durable `publication_blocked` flag prevents permanent/exhausted errors from silently regaining broadcast permission during later chain monitoring. Known TXIDs continue to be checked even after exhausted attempts: a delayed transaction may still be included. Current-chain queries recheck confirmed records, not just pending work. Confirmation depth is Core's `tip height - inclusion height` (not wall-clock time and not plus one). A missing/pruned TxPoW is **unavailable**, never confirmed. A changed known inclusion block identifies reorg. Node outages remove current positive verification rather than retaining a green result.

## Configuration and running

Ordinary Gateway/PostgreSQL/MiniDapp launch remains in [Gateway + Simulation](GATEWAY_SHIPMENTS_SIMULATION.md). For a safe local preview use `PROOF_MODE=test` with the existing authorized server simulator. This makes labeled local receipts only and does not contact Minima. `disabled` does not create new proof work.

Live mode requires **all** of:

| Variable | Value |
| --- | --- |
| `PROOF_MODE` | `live` |
| `PROOF_ALLOW_LIVE` | literal `true`, explicit operator permission to publish selected backlog/new events |
| `MINIMA_RPC_URL` | private writer RPC origin, HTTPS or loopback HTTP |
| `MINIMA_RPC_CREDENTIAL_FILE` | absolute path to writer JSON secret file |
| `MINIMA_READER_RPC_URL` | trusted reader node RPC origin; ideally independently operated |
| `MINIMA_READER_CREDENTIAL_FILE` | absolute path to read-only JSON secret file |
| `MINIMA_PUBLISHER_ADDRESS` | dedicated Core wallet address, `0x` + 64 hex characters (not Mx shorthand) |
| `MINIMA_CHAIN_ID` | `0x00` mainnet, `0x01` testnet; default `0x00` |
| `PROOF_CONFIRMATION_DEPTH` | integer 1–100; default 6 |
| `PROOF_MAX_ATTEMPTS` | integer 1–10; default 5 |
| `MINIMA_RPC_CA_FILE` / `MINIMA_READER_CA_FILE` | optional trusted CA certificate paths; no TLS verification bypass |

Secret files are UTF-8 JSON objects with `username` and `password`. They must be regular files, mode 0600 or stricter, at most 4 KiB, outside the repository, readable by the Gateway process. Do not put credentials in URLs, browser storage, CLI arguments, frontend bundles or committed env files. The reader must have Core read-only RPC access. The writer necessarily has wallet authority; isolate it on a trusted host. Node seed backup, wallet unlock and funding are operator responsibilities.

On the trusted Core host, consult that installed version's `help command:rpc` and configure RPC with authentication, TLS/private network binding/firewall. Official commands include `rpc enable:true password:<secret> ssl:true` and `rpc action:adduser username:<reader> password:<secret> mode:read`; enter secrets through the private operator console, not logged shell scripts/history. Never expose wallet RPC publicly. Verify `status`, the chain/network and dedicated `getaddress` before enabling publishing. Minima user UID is not used for authentication.

Native launch, after setting the variables above through your private process supervisor/environment:

```sh
npm --prefix services/gateway ci
npm --prefix services/gateway start
```

For live mining set `SHUTDOWN_TIMEOUT_MS=150000` and give the supervisor/container at least 160 seconds of stop grace. Mining RPC has a 130-second total deadline, reads 10 seconds; forced termination is still resumable from durable checkpoints. A healthy DB `/readyz` is not a claim that Core is connected or confirmations are current.

Base Compose accepts only disabled/test mode. Use a private Compose override for live, explicitly mapping all live variables, private HTTPS RPC endpoints, read-only secret file bind mounts (owned/readable by container UID 1000, mode 0600), CA files, `SHUTDOWN_TIMEOUT_MS` and `stop_grace_period: 160s`. Do not put live secrets in the base Compose or Docker image. Container loopback is not the host node: use private HTTPS endpoints reachable from the container or run Gateway natively beside the node. Do not weaken endpoint/TLS checks to reach host HTTP RPC.

### First real transaction (operator action, not run by tests)

1. Back up PostgreSQL and the dedicated wallet. Inspect selected existing outbox backlog: live mode processes that backlog as well as new events. Start on an explicitly configured test network first. Confirm both node versions/chain, synchronization, authenticated RPC, spendable self-transfer balance and publisher address independently.
2. Run an authorized server simulation or choose an existing important event. Its source remains `synthetic`. With `PROOF_MODE=test`, inspect its bundle and hash chain before any live attempt.
3. Stop Gateway, configure the live variables/secret files, then start it. Enabling both live switches is the explicit command that allows real publication. Observe proof attempt/state records on the private DB. Do not manually execute a second `txnpost` while a publication result is uncertain.
4. In authenticated Gateway `/app/#proofs`, inspect mode, provenance, hash, actual TxPoW ID, last check and depth. `submitted` is not verified. Wait for current-chain `included`/`confirmed`, then use Verify and export the bundle.
5. Verify the exported artifact using a separately trusted full node and the trusted publisher address, as below. Record the real TXID and Core/network version in your deployment validation log. This repository contains no fabricated real-TX example.

## Tenant API and MiniDapp

All endpoints require existing tenant authentication and `read` scope. Cross-tenant IDs return 404. Browser POST verification also requires the existing same-origin session/CSRF checks. No public RPC proxy, caller-selected URL, signing endpoint, arbitrary command or publisher control is exposed.

```
GET  /v1/shipments/:shipment_id/proofs?limit=50&cursor=<proof_uuid>
GET  /v1/proofs/:proof_id
GET  /v1/proofs/:proof_id/bundle
POST /v1/proofs/:proof_id/verify   JSON {}
```

Lists include actual TxPoW ID (`txpow_id`), transaction ID, event/type/sequence, mode, provenance (commitment), state, configured depth, observed confirmations and check timestamp. No wallet credentials, signed/mined blobs or internal RPC transcripts are exported. Bundle schema v1 contains the public proof plus complete cargo records through its anchor. Exports are limited to 2,000 records, conservative 3.5 MB canonical payload preflight and 4 MiB final JSON. Larger shipments need segmented verification in a future version; this API fails explicitly rather than truncating proof history.

Verify reconstructs the canonical records/hash chain/commitment before querying the configured reader. It checks transaction input/output publisher identity, a standard `RETURN SIGNEDBY(...)` wallet witness with signatures, port/data, final ID, network, current inclusion block membership, stable tip and depth. Return fields include `verified`, `status`, `reason`, `confirmations`, `hash_chain_valid` and `checked_at` where available. Bad/incomplete bundles, unavailable chain data and test receipts return `verified:false`. Verification uses one in-flight request per Gateway, with a one-second start cooldown; callers may receive 429. No transaction is sent by Verify.

The MiniDapp Proofs screen displays the above fields plus Verify/Export actions. It labels test mode and the absence of a blockchain TXID. Refreshing Gateway data does not turn a stored `confirmed` observation into an independent verification. The static Core-origin Preview has no wallet publishing authority and remains separate. Actual `/app/` sessions use the existing trusted Gateway-served same-origin transport; no unsupported MDS cross-origin proxy was introduced. Legacy ES5/Rhino service files are unchanged.

## Independent verification

An exported bundle can be checked without trusting Gateway's stored proof state, confirmation count, digest claims or verification result. Use a **trusted validating full node** that can still serve the transaction and inclusion block. This verifier relies on that node's consensus validation/authenticated transport; it is not a standalone light-client/SPV implementation and does not defend against a dishonest selected node. Provide the expected publisher address/network out of band, not just the bundle's own assertion. Checking publisher outputs alone is insufficient; inputs must also belong to that dedicated address.

```sh
# Use your independent read-only RPC and secret file; no publishing switch required.
export MINIMA_READER_RPC_URL=https://your-private-independent-node:9005
export MINIMA_READER_CREDENTIAL_FILE=/absolute/private/reader.json
export MINIMA_PUBLISHER_ADDRESS=0xYOUR_64_HEX_PUBLISHER_ADDRESS
export MINIMA_CHAIN_ID=0x01
export PROOF_CONFIRMATION_DEPTH=6
node services/gateway/src/proofs/verify-cli.js /absolute/path/exported-bundle.json
```

Exit codes: 0 verified on current chain at requested depth, 1 not verified, 2 invalid local configuration/input. A positive result concerns this specific prefix/commitment and observation time. For a TXID-only manual check use `txpow txpowid:<id>`, `txpow onchain:<id>`, `txpow block:<height>` and `status` on your reader, then use the bundle CLI to rebuild and compare the STATE commitment. A TXID alone cannot reconstruct private event data. Share the bundle only with authorized verifiers.

## Tests and diagnosis

```sh
npm --prefix services/gateway test
TEST_DATABASE_URL=postgres://... npm --prefix services/gateway run test:integration
node --test tests/minidapp/core.test.cjs tests/minidapp/browser.test.cjs
TEST_DATABASE_URL=postgres://... node --test tests/minidapp/server.integration.cjs
python3 scripts/package-minidapp.py /tmp/trackium-proof-review.mds.zip
```

Integration tests create/drop isolated schemas in the supplied disposable database. They cover exact canonical hashing, tampering/gaps, provenance/mode separation, current inclusion/depth/reorg, unavailable/pruned data, official command DTOs including hexadecimal case, authenticated RPC header spelling, secret-redacted audits, tenant auth, bounded exact-artifact rebroadcast after ambiguous send, worker exclusion/restart, browser Verify/export and existing simulator/legacy behavior. Mock Core tests never invoke a real node; enabling live publication is never part of test setup.

- `UNSUPPORTED_CORE_VERSION`: compare the pinned source contract before upgrading; do not disable version validation blindly.
- `RPC_AUTH` / `RPC_CREDENTIAL_FILE_UNAVAILABLE`: check file ownership/mode, RPC user and private node setup. No credentials are echoed by errors.
- `TXPOW_UNAVAILABLE`: node may be unsynchronized or data pruned. Use an archival node/retained data; this is not confirmation or proof of reorg.
- `CHAIN_TIP_CHANGED`: retry verification on a stable snapshot; no positive result is retained from inconsistent reads.
- `COMMITMENT_MISMATCH` / hash-chain errors: inspect the original bundle/journal; do not rewrite immutable history or automatically create a replacement transaction.
- `retryable_error` / exhausted attempts: inspect sanitized attempt records and the known final ID before operator intervention. `started` may mean a crash. Never reset/delete mined identity to bypass ambiguity.
- Confirmed observations can become unavailable/reorged on later checks. A stopped Gateway has no freshness guarantee; use independent verification.

Remaining limitations: real Core publication/restart/reorg acceptance still needs operator validation; global serial throughput is intentionally low; re-mining expired/conflicting published spends needs an explicit recovery design; no segmented bundles or automated archive retrieval, external signing/HSM, quorum/light-client verification, retention/pruning policy or production monitoring. RPC audit/state tables grow over time and require a reviewed retention/backup policy. Authorized cargo writers can consume publishing capacity/signing-key uses; Managed deployments still need quotas and a publication-approval policy. The real GL110-GL still needs an authoritative protocol, authenticated device/tenant binding and captured firmware-specific fixtures; synthetic proof publication does not supply these.
